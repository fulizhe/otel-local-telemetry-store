# "数据少了"有五种形态，各计各的，不合并成一个数字

一个本地有界存储被质疑时，第一反应是"存少了"。但"少"至少有五种成因，其中两种是**预期行为**、一种是**有意为之**、一种**在原理上无法计数**。把它们合并成一个 `lostTotal` 会同时丢掉两件事：故障定位能力，和"这是正常容量到顶"的可解释性。

**决策**：五种形态各自独立计数，**不做求和**。读口按"是不是故障"标注每一项的口径。SDK 自监控 scope 被过滤属于第六种 —— 那是**有意排除**，不计入任何"少了"的计数。

## 五种形态

| # | 形态 | 成因 | 是故障吗 | 能否计数 |
| --- | --- | --- | --- | --- |
| 1 | **队列丢弃** | 我们的有界队列满 | **是** —— 降级中 | 能，且精确 |
| 2 | **环形覆盖** | 环形文件写满，最旧块被覆盖 | 否 —— 容量到顶的正常结果 | 能，且精确 |
| 3 | **载荷拒写** | 单条 payload 压缩后仍超 `max.payload.bytes` | 看规律 —— 偶发可接受，成片出现说明上限配小 | 能，且精确 |
| 4 | **SDK 层截断** | `SpanLimits` / `LogLimits` 裁掉 attributes / events / links | 看配置 —— 数据本来就不全 | **不能**（已验，见下） |
| 5 | **head sampling 丢弃** | 压根没产生记录，我们从未见过 | 否 —— 配置使然 | **不能**（见下） |

**第 4 与第 5 是同一类黑箱**：都不产生信号，都只能靠与外部期望值对照发现。

## 关键约束：第 4 种已验为完全静默

A/B 实测（agent 2.32.0 + SDK 1.66.0，`docs/notes/2026-10-04-r0-extension-points.md` 第八节）：

设 `otel.span.attribute.count.limit=2`、`event.count.limit=1`、`link.count.limit=1`，造一个带 6 个 attributes、3 个 events、3 个 links 的 span：

| | 无限制 | 限额 2/1/1 |
| --- | --- | --- |
| 到达的 attributes | 6 | **2** |
| 到达的 events | 3 | **1** |
| 到达的 links | 3 | **1** |

三种截断都确实发生，但：

- **不产生任何新指标** —— 两组运行采集到的指标名集合完全相同（差集为空）
- **没有任何日志或警告** —— 输出里搜 `limit` / `truncat` / `discard` / `dropped` 零命中
- **`SpanData` 上没有任何标记** —— `getAttributes().size()` 就是 2，从数据本身看不出"本来有 6 个"

唯一残留线索是 SDK 内部类 `AttributesMap.totalAddedValues` 仍记着原值 6，但 `Attributes` **公共接口只有 `size()` 与 `asMap()`**，读它等于依赖 internal API —— 与 ADR-2 拒绝用内部 encoder 是同一条理由，不因这里"就差一个字段"而破例。

**因此第 4 种不可计数，处置与 sampling 相同**：落在文档与对照里，不进计数器。

## 关键约束：第 5 种在原理上无法计数

采样发生在产生记录**之前**。上游产生了几条我们看不到，所以"我们收到 3 条"无法反推"应该有 5 条"。

SDK 自带的 `processedSpans` / `processedLogs` 计的是 **autoconfigure 那个 `BatchSpanProcessor` 的丢弃**，不是我们的队列，也不是采样 —— **不能用它代替第 1 项**。我们的丢弃必须自己计。

因此**发现采样影响只有一条路：与外部期望值对照。** demo-app 的 `GET /demo/stats` 就是这个期望值来源 —— 它记录"本应用造了多少"，与库里实际条数对账，差额即采样 + 丢弃 + SDK 截断的合计。这是 demo-app 除可视化之外的第二个硬用途，也是它在主体落地前就有价值的原因。

## 环形覆盖的交叉验证

第 2 种要能与第 1 种区分开，靠两条已有能力交叉：`isOverwritten(id)` 判"这个逻辑位置是否已被新块占用"，`getOldestLiveIndex()` 给出当前可读窗口的左端。若最早存活 payload 的指针落在窗口左端之外，说明写指针与物理位置已经错位 —— 那是**故障**（写入路径出问题），不是容量到顶。

这条继承自 SkyWalking 侧的同名经验，且那侧的 bug 模式（把"从未写入"报成"已被覆盖"）一并继承：两者必须分开计数。

## 读口怎么呈现

按"是不是故障"分组，不按数字大小排序：

- **故障**：队列丢弃、载荷拒写（成片时）
- **容量**：环形覆盖、载荷拒写（偶发时）
- **配置（无法计数，只能靠对照）**：SDK 层截断
- **有意为之**：sampling（且只给对照，不给数字）
- **有意排除**：自监控 scope（不进任何"少了"）

**口径写在读口页面上，不靠口口相传。** 这是从 SkyWalking 侧继承的一条经验：段数 ≠ 链路数那类误解，本质是口径没写在页面上。

## Considered Options

- **合并成一个 `lostTotal`**：拒绝。这是本 ADR 存在的理由。合并后无法回答"是磁盘满了还是我在丢数据"，而这两个问题的处置完全不同（一个是调容量，一个是查降级）。
- **用 SDK 的 `processedSpans[dropped=true]` 当丢弃计数**：拒绝。它计的是 autoconfigure 的 `BatchSpanProcessor`，不是我们的队列；而且它自己也只覆盖 SDK 那一段。用它会同时错报两处。
- **对 sampling 做估算**（例如按 `samplerId` 反推比例）：拒绝。采样的决定发生在 SDK 内部且不可观测，任何估算都是编的。写一个假数字进读口比不写更糟 —— 用户会信它。
- **把"有意排除"也算进丢失**：拒绝。自监控 scope 被过滤是我们主动做的决定（ADR-1），混进"少了"会让过滤看起来像故障。
- **给环形覆盖报警**：拒绝。容量到顶是**这个产品存在的意义**（有界），对它报警等于对正确行为报警。要展示的是"现在写了多少圈、离最近一次覆盖多久"。
- **把第 4 种按"可计数"写进实现**：拒绝 —— 已验为完全静默，见上。想读 SDK 内部 `AttributesMap.totalAddedValues` 是破例依赖 internal API，与 ADR-2 拒绝内部 encoder 是同一条理由，不因"这里就差一个字段"而开口子。

## Consequences

- 读口至少要有 6 个独立计数器 + 1 组对照数据（demo-app 的 `/demo/stats`），而不是一个数字。这是 Phase 5 的硬需求，别到那时才发现"原来要这么多指标"。
- `CappedFileStorageStats` 已经给了第 2、3 种的底子（`expiredReadCount` / `oversizedRejectedCount`），Phase 4 只需把第 1 种接上并在更高一层汇总。
- 第 4 种已验为完全静默，**Phase 4 的实现里不要去找截断信号** —— 找了也找不到。它只能与第 5 种一起靠对照发现。
- demo-app 从"造数据的靶子"升级为"采样与丢弃的对照基线"。它的 `spans` 计数与库里条数的差额，是唯一能在原理上发现采样影响的手段。
