# HTTP 读口只开一个端口；端点清单封闭、JSON 手写编码；自监控指标不入库、也不过缓冲

Phase 4b 落地后，数据已经真的存在进程里，但**只有一个别扭的出口**：JMX。属性只能是
`String`/`int`，查询得逐个具名方法点，浏览器完全看不了。Phase 5 要补 HTTP 读口。
本文把**对外那张脸**一次定死 —— 端口、端点清单、返回形态、鉴权、自监控指标往哪放、
详情页的载荷怎么解、扩展自己的日志怎么在线看。

## 面对什么

- 「数据不出机器，但看得见」是本产品的价值主张，而"看得见"目前只有 JMX，**不成立**。
- ADR-1 已经定了：默认开启、默认绑 `0.0.0.0`、token 鉴权、只注册 GET/HEAD、
  **永远不提供 raw SQL**、端口冲突退随机。最后两条都需要一个**封闭清单**才能落实 ——
  清单开放，加一个 `/query?sql=` 就只是"顺手"。
- 端口退随机是 ADR-1 的决定，但**"怎么找到实际端口"从来没被设计过**。
- 我们的采集管线里正流着 agent 的自监控指标（`otel.javaagent.*`），
  `MetricTap` 按 scope 前缀把它们**丢掉了**（ADR-1 原则 2、ADR-2「自监控指标的过滤」）。
  ADR-2 写的是"这些指标走 JMX 面板" —— **那个面板至今不存在**。
- 载荷是编码后的 OTLP bytes（ADR-2），今天读回只有 hex。**详情页要显示 attributes /
  events 就必须解码**。

## 怎么定

### 一、一个端口，而且只有 HTTP 有

| 通道 | 端口 | 理由 |
| --- | --- | --- |
| **HTTP 读口** | **1 个** | 默认无鉴权（要 token 需显式配）、只 GET/HEAD、冲突退随机 |
| JMX | **0 个** | 走进程内平台 MBeanServer。**不开 JMX remote**（RMI/JMXMP）—— 远程 JMX 默认无鉴权，而读口里装着 trace 与日志载荷（SQL 语句、HTTP header、日志原文）；它还是应用的 JVM 参数，不该由我们替用户决定 |

所以"开一个新端口"的只有 HTTP 那一个。JMX 保持零网络。

**存储层开不起来时，读口照起**（2026-10-05 补记）。原来的代码注释写的是"存储不可用时不起：
挂一个只会报'没有存储'的空读口，比没有更容易误导"，而那条判断**没有任何决策记录**，
现在也不成立了：

- **排障最需要信息的时候，恰恰是最需要读口的时候。** 数据目录不可写是常见的部署事故，
  而那种情况下现在的行为是**整个读口不存在** —— 排查的人只能去翻应用的 stderr，
  连"队列还在收、只是没落盘"这个最要紧的事实都看不到。
- "只会报没有存储"是**把话说错了**。读口能报的比"没有存储"多得多：
  生效配置、三条队列的实时计数、`storeDegradedReason` 的**具体原因**
  （路径不是目录 / 权限被拒 / 文件被占用 / 建表失败，每一种的下一步都不一样）。
- 一个说清楚"我 degraded 了、原因是 X、队列还在收"的读口，
  比"连不上"有用得多。**误导的根源是说得含糊，不是说得悲观。**
- 代价：多一个"页面开着但没有数据"的场景。页面本来就分得清
  "没有存储"（`store: null`）与"存储是空的"，所以这个代价是可接受的。

`storeDegradedReason` 因此放在 `/api/summary` 的**顶层**、而不是 `store` 里面 ——
塞进去就得把 `store` 从 `null` 改成 `{}`，正好破坏"没有存储"与"存储是空的"这条区分。

### 二、端口发现：`*.port` 文件 + 启动日志，两样都做

- 先试 `otel.localstore.port`（默认 17890），`BindException` 则退到**随机端口**。
- **实际端口写进 `<dataDir>/otelstore.port`，每次启动覆盖写** —— 进程崩了没关的话，
  残留文件会报一个错的端口，这比没有文件更坏。
- 同时打一行 `读口就绪 host=… port=…`：文件给程序读，日志给人看。
- **端口配置不允许填 0**：绑定 0 让 OS 挑确实省事，但用户没法预先在防火墙上开口子。

### 三、端点清单（封闭清单；以后加端点要写 ADR）

| 端点 | 返回 | 说明 |
| --- | --- | --- |
| `GET /`、`GET /index.html` | HTML | **索引页**：概览 + 各页面入口。**不含任何数据表** |
| `GET /traces.html` | HTML | span 列表页（**不含数据**，数据由页面 JS 去取） |
| `GET /logs.html` | HTML | 日志列表页，同上 |
| `GET /metrics.html` | HTML | 指标点页，同上 |
| `GET /self.html` | HTML | **扩展自身**页：生效配置、库状态、自监控，同上 |
| `GET /self-log.html` | HTML | **扩展自己的日志**页：自有日志的尾部，刷新频率与自监控页不同（第十三节），同上 |
| `GET /app.css`、`GET /app.js` | CSS / JS | 各页面共享的样式与脚本，见第十三节 |
| `GET /api/summary` | JSON | **唯一的自监控面**：生效配置 / 三条队列 / 各表行数 / 两个环的写游标与覆盖轮次 / 淘汰计数 / 启动时间与实际端口 / agent 版本 / 存储降级原因 / 自监控指标丢弃计数（见第八节） |
| `GET /api/traces?limit=&traceId=` | JSON | span 表头行（**不含载荷**），默认 20、上限 200 |
| `GET /api/logs?limit=&traceId=` | JSON | 日志表头行，同上 |
| `GET /api/metrics?name=&limit=` | JSON | 指标点，`name` 缺省按 ts 倒序 |
| `GET /api/traces/{id}` | JSON | 单条 span + 已解码的载荷，见第七节 |
| `GET /api/logs/{id}` | JSON | 单条日志 + 已解码的载荷，同上 |
| `GET /api/self-log?lines=` | JSON | 扩展自己日志的尾部若干行，默认 100、上限 500（见第九节） |
| `GET /metrics` | text | Prometheus 文本端点 |

- **只注册 GET/HEAD。** 没有 POST/PUT/DELETE，连 OPTIONS 都不注册（不开 CORS，见下）。
- **没有"任意表 + 任意条件"的通用查询**，也没有载荷下载口。每个查询都是一个具名端点：
  口径写在路径与参数名里，不让人去记"哪个表有什么列"，同时守住 ADR-1 的"不提供 raw SQL"。
- `limit` 的上限**按用途分档**，不是全局一个数：

  | 端点 | 缺省 | 上限 | 为什么 |
  | --- | --- | --- | --- |
  | `/api/traces`、`/api/logs` | 20 | **200** | "看一眼最近几条"，200 条一屏已经翻不完 |
  | `/api/metrics` | 20 | **2000** | 它是**看趋势**的：最近半小时 × 每秒一个点就是 1800 条，沿用 200 会让这个既定用途**根本取不出来**（第八节） |
  | `/api/self-log` | 100 | **500** | 日志尾部，早已定下 |

  上限的意义是"别让读口变成导出工具"，**不是"越少越好"** ——
  指标那条从 200 抬到 2000，是为了让既定用途成立，不是为了多给数据。
  任何一档再往上抬，都要重新审视它对应的用途本身。
- `/metrics`（Prometheus）**不按 `limit` 取点**：它走"每个序列恰好一行"的口径（第十一节），
  返回的是当前值而不是时间序列，所以这条对它不适用。

### 四、鉴权：**默认不要求 token**；要 token 时用请求头，不用 URL

**默认无 token**（2026-10-04 决定，与初版相反，初版是"数据端点一律要 token"）。
理由与后果写在 [adr-01](adr-01-scope-and-principles.md) 的 Consequences 里，一句话版本：
这个扩展的定位是"挂在**本机**应用里自查"，默认要 token 会给最常见的用法加一道
"去文件里复制 token 粘进页面"的工序，而那道工序挡不住真实威胁。

- `/api/*`、`/metrics`、`/` **一律不要求 token**（默认配置下）。
- **`auth=true` 时才启用鉴权**，此时：
  - `/api/*` 与 `/metrics` 要求 token，放在 `X-Otel-Store-Token` 请求头里 ——
    **不用 query 参数**，它会进浏览器历史与 access log。
  - token 仍按 adr-1 每进程随机、写 `<dataDir>/*.token` 与启动日志，
    **绝不进入任何响应体、日志或异常消息**。
  - Prometheus 侧对应 `authorization.credentials_file`。
- **启用鉴权时，`/` 页面需要一个"粘贴 token"的输入框**，值存 `sessionStorage`
  （关标签页即失效），由页面里的 JS 带上那个头。
  这是唯一同时满足"token 不进 URL、不进 cookie、浏览器能自动刷新"的做法：
  - URL 带 `?token=` → 落浏览器历史；
  - `Set-Cookie` → token 进入之后每个请求，传播面扩大；
  - 页面本身也要 token → 浏览器普通导航带不了 header，人根本打不开。
  默认无 token 时这个输入框不显示。

- **无鉴权且绑定地址不是回环时，必须在启动日志里打一条显著警告**：
  说明任何人都能读全部载荷、以及配 `auth=true` 的方法。
  默认 `host=0.0.0.0`（adr-1）意味着这条警告**默认就会打** ——
  这是"默认方便"这个选择的必然成本，把它藏起来才是真的危险。

### 五、跨源：不解决，因为不需要

`/` 页面由**浏览器直接打开读口那侧**（`http://<host>:17890/`），因此
**不开 CORS**、demo-app 也不加代理、不加任何本地转发。
代价：那个页面不在 demo-app 的导航里，要另开一个标签页。
换来的是少一个开放面（开 CORS 等于允许任意站点来读你的 trace）。
ADR-1 里悬着的"读口跨源取舍"到此关闭。

### 六、返回形态：手写 JSON 编码器，不引序列化框架

- 只支持 `Map` / `List` / `String` / `Number` / `Boolean` / `null` —— **我们输出的一切形状都是自己造的**。
- **不引 Jackson / Gson**：省下约一百行代码，代价是 relocation、版本选择、
  以及"字节码必须 52"这条约束再核一遍（ADR-5 的教训）。不值得。
- **不支持任意 POJO 反射**：将来有人想输出自定义对象时，编码器**抛错**而不是静默输出 `{}` ——
  宁可构建期/运行期炸掉，也不要给出一个空的字段。
- 错误统一形态：HTTP 状态码 + `{"error":"…","kind":"…"}`。**不含栈**（栈进扩展自己的日志）。
- Prometheus 端点**不走 JSON**，是另一种文本格式（另一只手写的小渲染器）。
  不要为了"统一格式"把它 JSON 化 —— Prometheus 的解析器不接受 JSON。

### 七、详情页解码 OTLP bytes（只解，不给下载）

- 读口需要把载荷里的 attributes / events / status 显示出来，所以要解码 protobuf。
- 解码逻辑放 `readout/payload` 一层，**只依赖 shade 之后的 proto 类**
  （`io.github.fulizhe.otelstore.shaded.io.opentelemetry.proto.*`），
  **不 import 任何 `io.opentelemetry.*`** —— 因此不破坏 ADR-1 的分层，
  而且它也是将来"换一套编码"时唯一的改动点。
- **不做原始载荷下载口**：hex 形态留在 JMX 里就够排障，
  少一个"能把整条 trace 原样拖出去"的口子。
- 体积天然有界：单条载荷受 `max.payload.bytes`（默认 1 MiB）约束，**解码最坏情况已经在配置里封顶**，
  不需要额外的截断口径。

### 八、自监控指标：不入库，也不过缓冲 —— 只计数与现读

**原本要解决什么**：回答"是业务没产生数据，还是 SDK 那边就丢了"（spec user story #10），
让人能一眼分清这三种完全不同的情况。

**原来的推理链，以及它错在哪**：ADR-1 原则 2 要求自监控指标不入库，于是 `MetricTap`
在采集口就不 `offer` 它们。原文进一步认为「"不入库"是设计，"不采集"只是当前实现的副作用」，
因此给这批数据配一个进程内**有界缓冲**（默认最近 200 个数据点）加一个 `/api/self` 端点。

**实测推翻了这条前提**（2026-10-05，agent 2.32.0）：过滤用的 5 个 scope 里，
只有 `io.opentelemetry.runtime-telemetry` 真有对应的仪表化模块，且清单版本是 `2.32.0-alpha`、
默认关闭；`io.opentelemetry.sdk.trace` / `sdk.logs` / `sdk.metrics` 与 `io.opentelemetry.exporters`
在 agent 的 **315 份仪表化清单里一份都没有**。

也就是说**默认配置下被过滤掉的那批是空的**。为一个不会到达的数据建缓存，
是为一份不存在的输入预留内存，而且 `/api/self` 会永远返回空数组却看不出原因。

**怎么定**

1. **过滤本身不动**（ADR-1 原则 2）：自监控指标仍然不写进任何业务表。
2. **不引入任何进程内缓冲。** 被过滤掉的批次**只计数** ——
   `selfTelemetryDropped` 与 `lastSelfTelemetryDroppedAt` 出现在 `/api/summary`。
   计数是 O(1) 内存，而且"过滤掉了多少个点"本身就是排障信息。
   静默丢弃会让人误以为"根本没有自监控指标这个概念"。
3. **保留全部 5 个前缀**，包括在 agent 2.32.0 里查无对应模块的那 4 个
   （`sdk.trace` / `sdk.logs` / `sdk.metrics` / `exporters`）。
   代价是几行字符串比较，收益是一道**不会误伤未来版本**的门 ——
   万一某个 agent 版本开始产出它们，删掉前缀就等于让它们静默进业务表。
4. **扩展自身的健康一律在请求时现读，零缓存。** 队列的
   `offered/drained/dropped/sinkErrors/backlog`、两个环形文件的写游标与覆盖轮次与最老存活 id、
   行数水位、已淘汰行数、存储降级原因 —— 全部是**已经存在的计数器**，请求时读出来就是实时的。
   **要"当前状态"从来不需要缓存；缓存只是为了要"历史"。**
5. **`/api/self` 取消。** 它在实现上只会是 `/api/summary` 中 `queues` 与 `store` 那部分的重复，
   而端点清单每多一个就多一处要维护（路由、鉴权、测试、文档、页面）。
   取消之后 `/api/summary` 是**唯一**的自监控面。
6. **业务指标的历史归业务层缓冲。** 我们不缓存，但业务层照常每秒发一个点，
   我们像收任何业务指标一样收下 —— 走的是已验收过的现成路径，零新代码。
7. `/api/summary` 为此补齐**平铺**的 5 个键（`actualPort` / `startedAt` / `uptimeMs` /
   `agentVersion` / `storeDegradedReason`）。分界线是清楚的：**`config` 是"配置"，其余全是"运行时事实"**；
   不嵌套成新的一组，因为那一组会长得很像刚被取消掉的 `/api/self`。
   前两个不是锦上添花：spec 的 Further Notes 要求"显示启动时间与端口，便于判断是不是同一份数据"，
   而单实例前提（ADR-4）意味着**两个进程指向同一个 `dataDir` 时会互相覆盖** ——
   取消 `/api/self` 之后，`/api/summary` 是唯一能让页面回答"这是不是同一个进程的数据"的地方。
   - `actualPort` 与 `config.port` **不是重复信息**：后者是配置值，前者是冲突退随机后的真实端口，
     两者不等就说明退让过。
   - `storeDegradedReason` 放在 `store` **外面**（`store` 为 `null` 时它才有值，
     健康时为 `null` 而不是缺键）—— 塞进去就得把 `store` 从 `null` 改成 `{}`，
     正好破坏"没有存储"与"存储是空的"这条区分。只取异常类型与 message，**不含栈**（第六节）。
     它与第九节的 `/api/self-log` 不重复：那个是日志尾部（会被轮转掉），
     这个是结构化、恒定存在的字段，只回答"为什么现在没落盘"。
   - 依赖注入沿用既有 `queuesSnapshot` 那个 `Supplier` 路子，**不让 `readout` 去 import `agentext`**。

**Considered Options**

| | 做法 | 为什么没选 |
| --- | --- | --- |
| 保留 200 点缓冲 + `/api/self` | 照原设计做 | 默认配置下**无数据可缓冲**，`/api/self` 永远返回空数组；为一个 `2.32.0-alpha` 且默认关的 feature 预留内存，还要多养一个端点 |
| 自监控指标入库（加 `self_metric` 表） | 让它们能查 | 违反 ADR-1 原则 2；且两类数据生命周期不同（业务按环有界淘汰，自监控按时间窗），混在一张库迟早对不上 |
| 继续丢弃、文档写明"没有自监控面" | 什么都不做 | 需求真实存在；而且"丢弃"这件事本身值得计数 |
| 我们提供"注册自监控快照"的 API | 缓存归业务层，扩展只持有引用 | 我们的 jar 因此多一张对外 API 面，且业务层从此依赖扩展 jar 的类型 —— 用一个**公开接口**换一个本来就不存在的需求 |
| 读口代理业务层的 HTTP 端点 | `/api/self` 转发业务层的指标历史 | 读口会开始认识具体应用、破坏封闭端点清单、多一个故障点（业务侧挂了读口跟着挂） |

**后果与接受的代价**

- 想要自监控指标的**历史**（比如"过去半小时 `otel.sdk.*` 怎么变的"），
  得开启 runtime-telemetry 并自己接一个 `MetricReader` —— **我们不再提供这个便利**。
  这是本节明确接受的代价：本项目对"每进程常驻内存"有纪律，而这个需求在默认配置下是空的。
- `/api/summary` 变胖（多 5 个键）。它本来就已经是那个"一眼看清扩展怎么样"的端点。
- **端点清单从 8 个减到 7 个。** 减端点同样要走决策记录 —— 这一节就是那份记录。
- 若将来 agent 改变那批指标的默认行为，本节需要重写；
  但届时 `selfTelemetryDropped` 会从 0 变成非 0，**那是一个可观测的信号，不需要靠猜**。

### 九、扩展自己的日志：只读自己写的那一个文件

- 扩展自己的日志由 **`SelfLog` 门面**写 `<dataDir>/otelstore.log`：轮转备份
  `<dataDir>/otelstore.log.1`，**单文件 1 MiB、只留 1 份备份**（合计有界 ≤ 2 MiB）——
  符合本项目"有界"的第一原则。各处的日志改调 `SelfLog.info/warn`：它**写文件**的同时
  **照常调 JUL**，所以 stderr / agent 那边的输出一字不变。
- **为什么不是"给 logger 挂一个 JDK `Handler`"**（2026-10-06 实测，见
  `docs/notes/2026-10-06-self-log-filehandler-probe.md`）：OTel javaagent 把
  `java.util.logging.Logger` 换成了 `io.opentelemetry.javaagent.bootstrap.PatchLogger`。
  在扩展的 ClassLoader 里，`Logger.getLogger(...).addHandler(...)` 是**空操作**
  （`getHandlers()` 恒为 0）、`setLevel(...)` 也不生效（level 恒为 SEVERE）——
  **挂着 agent 时挂 Handler 收不到任何记录**（这正是真机首次验收返回"暂无内容"的原因）。
  改由扩展自己的门面直接写文件，不依赖 JUL 是否被替换；用的仍是 JDK 的
  `java.util.logging`（`LogRecord` / `Formatter`）与 `java.io`，零三方依赖。
  同一份 notes 里还记着 `FileHandler` 的 `count` 是"文件总数"而非"备份份数"那件事。
- `/api/self-log` 读它的**尾部 N 行**（默认 100、上限 500）。
- **只读这个文件，不读应用的日志、也不猜 stderr 去了哪**：
  stderr 落哪个文件由启动方决定，扩展无从得知；而为了展示自己的状态去读
  **别人的**日志文件等于伸手到不该碰的地方，还会把应用的日志内容复制到读口页面上，
  直接扩大 token 的泄露面。
- 代价：扩展的日志出现两处（stderr 给运维 `tail`，这个文件给页面），内容相同、消费方式不同。
- 编码跟随平台（`FileHandler` 的限制）。**同进程内读写永远一致**，读口接口不受影响；
  把这个文件拷到另一台机器看可能乱码 —— 那是运维自己制造的问题，不是接口的缺陷。


## 十一、`/metrics` 的标签只有 `attr_key` 哈希 —— **这是已知的取舍，不是 bug**

Prometheus 的价值在标签上（`region="east"` 与 `region="west"` 分成两条线）。
而 `metric_point` 表**只存了属性组合的哈希、没存属性本身**（ADR-2 的表定义），
所以本阶段的 `/metrics` 只能输出：

```
orders_processed_total{attr_key="a3f9c2e1",otel_scope_name="…"} 3
```

**这不好，但比三个替代方案都便宜**：

| | 做法 | 为什么没选 |
| --- | --- | --- |
| 加 `attr_text` 列 | 存属性规范化文本（`resource_dict` 已有同一套规范化） | **要多改一次 schema 与 mapper**，而本阶段的重点是把端点铺完；标签这件事等 metrics rollup 那段一起做更省 |
| 不出标签、同名合并 | 每个指标名只出一行 | **错的**：不同属性组合的值会被加在一起，Prometheus 直接给出错误数据 |
| 把哈希伪装成属性名 | 输出 `{region="a3f9c2e1"}` | **更坏**：那是撒谎，读者会以为 `a3f9c2e1` 是个真属性 |

同时定下三条口径（ADR-6 第十一节有完整理由）：

- **`SUM` 不改名成 `_total`**。Prometheus 的 `_total` 约定隐含"单调递增"，
  而我们**没有持久化 `is_monotonic`**（ADR-2 的表里没这列），改名就是撒谎。
  只用 `# TYPE` 声明它是 counter。
- 标签给 `attr_key`、以及非空时的 `unit` 与 `otel_scope_name` / `otel_scope_version`。
- 指标名里的非法字符按 Prometheus 约定换成 `_`，**撞名时追加 8 位哈希后缀**
  （`a.b` 与 `a_b` → `a_b` 与 `a_b_1f3e9a2c`），保证可逆、不丢信息。

**将来要补的**：`attr_text` 列 + 用真属性当标签。已记在 `docs/adr/index.md` 的「悬着的事」。


## 十、列表端点：空数组、参数校验、以及 Resource 就地展开

`/api/traces`、`/api/logs`、`/api/metrics` 是同一套形态。四处口径在这里定死，
因为它们都是"看起来像小事、错了却很烦"的地方。

### 没有数据返回空数组，不是 404

`traceId` 合法但库里没有 → **200 + `[]`**。
把"没有数据"报成 404 会让脚本分不清"这个 trace 不存在"与"我请求写错了"，
而这两种情况的处置完全不同（前者正常，后者改代码）。只有**参数非法**才 4xx。

### `traceId` 要做格式校验，明显非法立刻 400

trace_id 恒为 32 位十六进制。一个明显不是 32 位十六进制的值（比如 `abc` 或中文）
**立刻 400**，不要拿它去查一次索引 —— 那是"用户还没发现自己的 bug，读口先替他查了一轮库"。

格式对但库里没有，是 200 + 空数组。**校验格式与校验存在是两件事。**

### 每一行就地带上 Resource 的规范化文本

行里除了 `resourceId`，再给一个 `resource` 字段，值是字典表那一列的原文。

- 页面直接渲染，不用为了显示"这是哪个服务的 trace"再发一次请求。
- 一页 200 行通常只对应两三种 Resource，所以**同一 id 只查一次**（`ReadoutQueries` 里那个
  归并不是锦上添花：碰上几十种 Resource 的应用时，它把每页 N 次查询压成个位数次）。
- JMX 那个读口把 Resource 作为**独立的 `resource_dict:` 段落**附在文本后面，
  与这里的行内字段**形态不同但数据同源**（都来自 `ReadoutQueries.resourceAttributesOf`）。
  形态必须不同：JMX 是给人看的文本，HTTP 是给机器与页面消费的数组。

### 超长字段的截断必须可见

`name` 与 `body_preview` 都可能很长。截断时**留一个显式标记**
（页面显示成 `…(共 N 字)`），不能让半截内容看起来像完整的 ——
"看起来完整但被截断了"比"明确写着被截断了"危险得多。

### `detail` 那一列结构化返回，且只有一处懂它的语法

`metric_point.detail` 是我们自己定的紧凑文本（ADR-2：`explicit;…;bounds=[..];counts=[..]`）。
Prometheus 渲染器与页面都要读它，所以**解析逻辑只有一处**（`MetricDetail`）：

- `/api/metrics` 返回**结构化**的 `detail`（`flavor` / `bounds` / `counts` / `quantiles`），
  而不是原样吐文本 —— 让页面与脚本各写一个解析器就是两套语法。
- **解析不出来时 `flavor` 为 `unknown` 且带上 `raw` 原文**。只给空结构的话，
  页面上什么都判断不了（是这个形态没覆盖，还是数据坏了？）。页面据此显示"认不出来"。
- 直方图的 `bounds` 与 `counts` **长度不等时直接当认不出来** ——
  "第 i 个桶的边界"在长度不等时根本无从谈起，硬凑只会画出错的直方图。

### 「不按名字过滤」与「名字是空串」是两件事

`/api/metrics` 缺 `name` 时要给**最近的所有指标点**，而不是"名字等于空串的那些"。
这条曾经写错过：把空串去做等值匹配，于是"看最近的所有指标"永远返回空 ——
而**空结果看起来完全像"还没有指标"**，既不报错也不像故障（JMX 的
`recentMetricPoints("")` 也就跟着一直返回空）。存储层现在显式把 null / 空串当作"不过滤"。

## 七、详情页解码 OTLP bytes（只解，不给下载）

读口需要把载荷里的 attributes / events / status 显示出来，所以要解码 protobuf。

- 解码逻辑单独一层（`readout.payload`），**只依赖 shade 之后的 proto 类**，
  **不 import 任何 OTel SDK / API 包** —— 因此不破坏 ADR-1 的分层，
  而且它是将来"换一套编码"时唯一的改动点。
  （源码里写的是 `io.opentelemetry.proto.*`，shade 时一并重定位到
  `…otelstore.shaded.io.opentelemetry.proto.*`；这不违反分层规则 ——
  规则的适用范围是 `core`，而解码本来就该与 OTel 数据模型待在一起。）
- **不做原始载荷下载端点**：hex 形态留在 JMX 里就够排障，
  少一个"能把整条 trace 原样拖出去"的口子。
- 体积天然有界：单条载荷受 `max.payload.bytes`（默认 1 MiB）约束，**解码最坏情况已经在配置里封顶**，
  不需要额外的截断口径。

### 载荷"不可用"有四种原因，必须分得开

一条 span 的载荷可能读不出来，而**这四种情况的处置完全不同**：

| `reason` | 含义 | 是故障吗 |
| --- | --- | --- |
| `no_payload` | 写入时被拒（超 `max.payload.bytes`）或编码失败，表头行在、载荷没有 | 看规律（ADR-3 第 3 种） |
| `expired` | 环形文件已覆盖 —— **过期是预期行为，不是故障**（ADR-3 第 2 种） | 否 |
| `corrupt` | 字节读到了但解不出 OTLP 结构 | **是**（写入路径或环文件有问题） |
| （行不存在） | 这一行不存在 → 整个请求 404 | 通常是 id 写错或已被水位淘汰 |

**混成一个 `available: false` 就等于把"正常过期"和"数据坏了"混成一件事** ——
而这正是 ADR-3 反复警告的"合并成一个 lostTotal"。所以 `payload.reason` 必须给出上面的值，
并且每种都带一句"这意味着什么"：用户看到"不可用"会自己去猜，而"过期"与"坏了"要他去的地方完全不同。

> 实现时踩过一次很典型的坑：`Read.of(bytes, overwritten)` 写成
> `bytes == null ? NONE : new Read(bytes, overwritten)`，于是**覆盖标志恰好在"读不到"的时候被丢掉**
> —— 因为"读不到"就是 `bytes == null` 的时候。结果"过期"全部退化成"没有载荷"。
> 这类 bug 不报错、能过大部分断言，只是把两种相反的处置混成一种。

### 详情端点用路径参数：`GET /api/traces/{id}`

这是清单里**唯一**的路径参数端点（`/api/logs/{id}` 同理），因此路径解析的口径必须定死：

- **只按前缀匹配固定前缀**（`/api/traces/` 后面那一段整体就是 id），
  **不做通配、不做多段、不做正则**。多一个 `{id}` 形态就多一处路由解析的风险，
  而收益只是一点"REST 味"。
- `{id}` **必须是纯数字**（上限 18 位，避免溢出成另一个 id），否则 400 ——
  不是数字的东西不该进到按主键查的代码里。
- 路径里出现 `/api/traces/1/2`、`/api/traces/../x` 之类时，因为不做多段匹配，
  整串会被当作 id 去解析 → 因非数字而 400。**没有路径穿越的口子**。
- 行不存在返回 **404**，而列表的"合法但没有数据"是 200 + 空数组 ——
  一个不存在的 id 是请求写错，空数组是"确实没有"。

## 十二、HTTP 服务器用 JDK 自带的 `com.sun.net.httpserver`

「读口不引入任何三方依赖」这条（第六节）有个前提问题：**谁来提供 HTTP 服务器？**
除了"自己写"，JDK 本身就有一个。

**决策**：用 `com.sun.net.httpserver.HttpServer`（模块 `jdk.httpserver`）。

**它的性质要说清楚**：JDK 自带、JDK 8 起就有，但它**不属于 Java SE 规范**，
属于 JDK 内部 API。用它的理由与代价：

| | 用 `com.sun.net.httpserver` | 自己用 `ServerSocket` 手写 HTTP/1.1 |
| --- | --- | --- |
| 代码量 | 约 300 行 | 约 600 行 |
| 依赖 | 零 | 零 |
| 风险 | 内部 API：跨 JDK 大版本可能变 | **自己实现 keep-alive 与 chunked**，错的地方都在"正常情况下测不出来"的路径上 |
| 跨 ClassLoader | 由 bootstrap / 平台加载器提供，我们的代码在扩展 CL 上调用它 —— **已实测可用**（真机跑通） | 同上 |

第三行是关键：手写省下的那三百行不是白赚的，代价是 HTTP 协议里最容易写错、
最难测出来的那几处（半包、chunked 边界、连接复用后的残留响应体）。
而"内部 API 可能变"这个风险，在这个项目里已经被别的东西兜住了 ——
**所有面向字节码版本的约束已经在 ADR-5 里核过一遍**（依赖必须 52），
多一条"HTTP 服务器来自 JDK 本体"并不改变那条约束的性质。

**已实测**（2026-10-04，真机挂 agent）：在 `ExtensionClassLoader` 上能正常起、绑定、
响应、读 jar 内资源。这是选它之前最不确定的一点，现在有答案了。

## 十三、页面是多个文件：按"一条线一页"拆，`/` 做索引

**面对什么**：把三条信号线、库状态、生效配置塞进一个 `index.html`（619 行），
一开始的理由是"只有一份公共代码，所以只能有一页"。这个理由一旦成立就再也拆不开 ——
样式与那 200 行 JS 助手都内联在页面里，想多一页就得复制一份，改一处漏一处。
而单页的直接后果是**打开 `/` 不知道自己在看什么**：读口有四类东西，
挤在一页里只能靠滚动去找。

**怎么定**：一页一条线，`/` 变索引页。

| 页面 | 只放什么 |
| --- | --- |
| `index.html` | 概览 + 各页面入口。**不放任何数据表** |
| `traces.html` | span 列表、trace_id 过滤、详情弹窗 |
| `logs.html` | 日志列表、详情弹窗 |
| `metrics.html` | 指标点、结构化 detail |
| `self.html` | 扩展自身：生效配置、库状态、自监控 |
| `self-log.html` | 扩展自己的日志（**刷新频率与自监控页不同**，所以单独一页） |

- **自有日志单独一页**：它的刷新频率与「扩展自身」不是一回事 ——
  配置与队列几十秒看一次就够，日志是**要盯着看的**（几秒一刷）。
  挤在同一页里，要么日志不新鲜、要么配置跟着白刷；频率不同的东西分页，
  这是"一条线一页"这条原则的自然推论。
- **共享样式与脚本由读口自己提供**（`/app.css`、`/app.js`），每页只声明
  自己渲染哪一条线。这条是上面那个"只能有一页"的死结的解法：**宁可多两个静态端点，
  也不要复制 5 份 200 行**。
- **页面零依赖**：不引 CDN、不引框架、不用构建。读口跑在客户应用里，
  不能假设有外网；而且页面是**增强项** —— 它坏了不该让 `/api/*` 也跟着坏，
  一个引 CDN 的页面在离线环境里会静默变成一片空白。
- **路径精确匹配，绝不把请求路径拼进 `getResourceAsStream()`。**
  资源名来自一张**硬编码常量表**，路径先查表，查不到就 404。
  这正是第七节那条"不做多段匹配"的同一个道理在静态资源上的应用 ——
  一旦让请求路径参与资源名拼接，`/../` 就是现成的穿越。
  因此 `/app.css/x`、`/app.css%2f..` 一律 404，**没有无后缀别名**（`/traces`）——
  少一条要维护的路径，索引页已经把入口给全了。
- **自监控页明确分两段**：「扩展自身」（生效配置、自监控计数器、扩展的异常）
  与「库状态」（各表行数、队列、环形文件、丢弃与过期计数）。
  「扩展自己的日志」不在这两段里，它是单独一页（见上）。
  这是两件不同的事 —— 混在一张卡片里，
  会让人把扩展的队列健康误读成被观测应用的遥测健康。
- **没有数据的地方就写"还没接上"**（并给出 issue 号与端点名），不摆占位数字。
  空槽位比假数据安全：假数据会被人拿去判断系统健康。
- **页面仍然不含数据**（第四节的结论不变）：数据一律由页面 JS 带头去取，
  所以页面本身不需要 token。

**Considered Options**

| | 拆多页 | 保持单页 |
| --- | --- | --- |
| 打开 `/` 知道自己在看什么 | 索引页一目了然 | 靠滚动猜 |
| 公共 JS | 一份，共享 | 一份（但这是"只能有一页"的原因） |
| 静态端点数 | 8 个页面/资源 | 1 |
| 端点清单封闭性 | 仍然封闭（硬编码表） | 仍封闭 |

**否决了"每页自带一份 CSS/JS"**：那会让 5 份副本各自漂移，
而修一处漏四处的 bug 只要一次。**否决了"做成单页 + 前端路由"**：
它要引框架（违反零依赖），而且把"打开哪个地址"这件事变成了客户端状态 ——
刷新一下地址就变了，粘给别人的链接对不上。


- **也开一个 JMX remote 端口方便远程监控**：拒绝。无论 HTTP 还是 JMX，**默认都不要求 token**
  （见第四节），而载荷装着 SQL 与日志原文；它还是应用的 JVM 参数。见第一节。
- **端口配置允许填 0**：拒绝。用户没法预先开口子，而"能预先开口子"是自部署场景的刚需。
- **开 CORS 让 demo-app 页面直接读**：拒绝。见第五节 —— 页面直接开读口那侧就不需要，
  而开 CORS 等于允许任意站点读你的 trace。
- **引 Jackson / Gson**：拒绝。见第六节。
- **给 `/api/*` 加 POST 做查询（body 里带条件）**：拒绝。只注册 GET/HEAD 是 ADR-1 的明文；
  POST 查询还会被中间代理与防火墙当成"写操作"拦掉或记录。
- **加一个 `/api/payload/{id}` 返回原始 bytes**：拒绝。见第七节。
- **自监控指标入库（加一张 `self_metric` 表）**：拒绝。违反 ADR-1 原则 2，
  且两类数据生命周期不同（业务数据按环有界淘汰，自监控指标按时间窗），混在一张库里迟早对不上。
- **继续丢弃自监控指标、文档写明"没有自监控面"**：拒绝。数据已经在管线里，
  白扔；而"SDK 健康吗"恰恰是本地自查的第一需求。见第八节。
- **读应用的日志文件在页面上展示**：拒绝。见第九节 —— 路径未知、越界、格式不保证，
  且那是 log collector 的活，不是遥测存储的活。

## 十四、指标页给趋势图：**只画能画对的，并说清画的是哪个量**

**面对什么**：指标点原本只有一张表。时间序列用表格看趋势很吃力 ——
"这个指标刚才是不是抖了一下"要靠人眼在二十行里前后扫。

**怎么定**：指标页表格之上加一张内联 **SVG** 折线图，与表格**共用同一次
`/api/metrics` 的结果**（不额外发请求，否则两张图可能不是同一份数据）。

**画什么，按形态分别决定，并把它写在图例上**：

| 形态 | 画的量 | 为什么 |
| --- | --- | --- |
| Gauge | `metricValue` | 它就是值 |
| Sum | `metricSum` | 单调累计，画累计曲线看总量走势 |
| Histogram / Summary | `metricCount` | **没有单一"值"**。画 sum 或 count 都是代理量，必须标明是哪个 |

- **绝不画"看起来最像值"的那个**。直方图没有值可画，
  把 `sum` 标成"值"就是在撒谎；而把代理量**写清楚**就不是。
- **没有对应数字的点跳过，不补 0**。补 0 会造出一段不存在的下跌。
- **一条序列 = 指标名 + 属性组合哈希**。属性本身读不出来（第十一节），
  所以图例只能给指标名加一段哈希 ——
  **不能拿哈希冒充属性名**。这是同一个取舍的第二次露面。
- **只画前 8 条序列，并写明还剩几条没画**（第十节那条规矩）。
- **只有 1 个时间点时不画线**，直接说"只有一个点，画不出趋势" ——
  画一个点再连成横线，会被读成"这段时间没变化"。
- **纵轴上下限与所画量一起标出**，避免把"两条平线"读成"两条一样高"。

**技术选型**：手写内联 SVG。理由与页面零依赖同源 —— 不引图表库（读口跑在客户
应用里，不能假设有外网），而 SVG 是文本、可嵌在 `innerHTML` 里、不需要 canvas
的尺寸与 devicePixelRatio 处理。图例、`<title>` 悬浮提示都直接是 SVG 元素。

**否决了**：

- **canvas**：要处理 devicePixelRatio 与重绘时机，为一个只读折线图引入一整套
  尺寸逻辑不值；SVG 直接随 CSS 缩放。
- **让服务端出 SVG**：那要给 `/api/metrics` 之外的端点加职责，而且图里的
  颜色与刻度是展示层的事，不该由存储层决定。
- **画出所有序列**：几百条线叠在一起既看不清也没有用，
  而"没画的还有 N 条"必须写出来，否则看起来就是全部。

## 十五、trace 瀑布：**后端零改动**，按来源分组、按 kind 上色，画不出就明说

**面对什么**：读口能落库、能读回、能画指标趋势图，但**"这个进程在跟谁打交道"看不出来**。
span 列表一列一行，父子关系要人眼比对两个十六进制串；有五六个 span 时就已经要来回横跳。
更不能回答"埋点到底挂上了没有" —— 那要靠看调用链的形状，而不是读一行行字段。

**怎么定**：列表行与详情弹框里的 trace 链接，**开出瀑布弹框**（不再是"跳到 span 页再筛"）。
内联 SVG，与指标趋势图同一套零依赖口径（文本、可嵌 `innerHTML`、随 CSS 缩放、不引图表库）。
横轴是时间，缩进是父子深度，条按 `startTime..endTime` 定位。

- **按 `scopeName` 分组、按 `kind` 上色**：来源徽标让眼睛认出这条链里有哪几种技术，
  kind 让眼睛认出**进程边界在哪**（SERVER / CLIENT / PRODUCER / CONSUMER / INTERNAL 各一色）——
  这正是 SkyWalking 拓扑图的视觉语言。**不伪造 `service.name`**：图上的来源就是仪表化真的来源。
- **点瀑布里任一条 → 复用现有的详情弹框**，不新造第二个。
- 点 trace 链接 → 瀑布；瀑布里点条 → 详情；Esc **先关最上面那层**。

**三条"不编"的纪律**（沿用第十四节"只画能画对的"那条自我约束）：

| 情形 | 怎么办 | 不怎么办 |
| --- | --- | --- |
| `parentSpanId` 全 0 | 当根 | — |
| **父 span 不在结果集里**（被行数水位淘汰 / 被上限截断） | 仍当根，图上**写明"父 span 不在库里"** | **绝不静默改挂到某个看起来差不多的祖先上** |
| 只有一个 span / 没数据 | **明说画不出**，只列出来 | 画一条横线 —— 会被读成"链路就这么长" |
| 条数或深度到上限 | 写明"只画了前 N 条" / "缩进到第 N 层封顶" | 让人把局部当成全部 |

**为什么后端零改动是本节的约束，而不是"暂时没找到要改的地方"**：
`/api/traces?traceId=` 已经按 `start_time ASC` 返回该 trace 的 span，且每行已含
`spanId` / `parentSpanId` / `startTime` / `endTime` / `kind` / `scopeName` —— 画图要的字段一个不缺。
**因此段 B 是纯前端改动**；将来真需要现在没有的字段（例如把 `db.system` 提成列，
好让两种数据库在图上直接可辨），那是**另一条决策**（会碰 ADR-2 的表头行口径），
**不许在画图时顺手加列**。

**否决了**：

- **服务拓扑图**：用户明确"以后再说"。它要单独定义 endpoint×component 的聚合口径，
  值得一张独立的 ADR；与"一条 trace 的时间轴瀑布"是两件事。
- **canvas / 引图表库**：与第十四节同源的理由 —— 读口跑在客户应用里，不能假设有外网。
- **在详情里渲染整棵树**：详情是"一条 span 的全部字段"，树是"一条链的形状"，
  两者折叠进同一个弹框会让两边都变差。
- **段 B 顺手给 `span` 表加列**：见上，那会破坏"后端零改动"这条约束本身。

## Consequences

- **对外表面从此封闭：加端点要写 ADR，减端点同样要写。**
  原文写的是"加端点要写 ADR，**改**端点不用" —— 第八节减掉 `/api/self` 让那句话不成立了：
  减端点一样改对外表面，一样要留下记录。清单小是刻意的，
  口径 proliferation 是这类存储最容易出的错（ADR-3）。
- **减掉 `/api/self` 不构成破坏性变更**：那个端点**从未实现过**，
  清单里只是一行"随 Phase 5 后续两段落地"。真正破坏兼容性的从来不是清单，
  是**已经能调用的东西会不见**。
- **`/api/summary` 成了单点**：取消 `/api/self` 之后，它是唯一的自监控面 ——
  队列、环形文件、水位、淘汰、降级原因、启动时间与端口全在它身上。
  这既是"少一个端点"的收益，也是**新的可用性前提**：
  它挂了，"这个进程现在怎么了"就彻底答不出来，而它现在还兼着自动刷新页面的数据源。
- **读口不引入任何三方依赖**：JSON 与 Prometheus 都是手写小渲染器，
  protobuf 解码用已 shade 的类。ADR-5 那条"升级依赖要核字节码 52"的约束不会因为 Phase 5 而增加。
- **少一处有界缓冲**：原来是两处（自监控旁路、扩展日志文件），现在只剩扩展日志文件一处。
  而那一处**还没实现** —— 也就是说这一轮结束时，进程内**一处自建缓冲都不剩**，
  存储全部交给 H2 与按环封顶的文件。这比"有界"更进一步：**没有可增长的东西**。
- **新增一条使用方义务**：想看业务指标的历史，**业务层要自己每秒滚一个点发出来**
  （见第八节）。我们不缓存，但也不假装需求不存在 —— 这条义务要写进使用文档，
  否则第一次用的人会以为"半小时历史"是自带功能。
- **指标点的 `limit` 上限从 200 抬到 2000**（第三节），响应体最坏约 500 KB。
  它是回环默认、手动打开的页面，但**默认绑 `0.0.0.0`** ——
  指标名与属性哈希会往外走（不含载荷）。抬上限的理由是让既定用途成立，不是多给数据。
- **页面不在 demo-app 里**：验收要另开一个标签页指向读口端口。
  这是"不开 CORS"的直接代价，写进使用文档。
- **配了 `auth=true` 时，"从命令行 curl 读口"要自己带 header**：
      `curl.exe -H "X-Otel-Store-Token: …" http://host:17890/api/summary`，
      token 在 `<dataDir>/*.token` 里。**默认无鉴权时 `curl.exe http://host:17890/api/summary` 直接就能读。**
- **读口线程里会做 protobuf 解码**：单条最坏 1 MiB（`max.payload.bytes` 封顶），
      批量由 `limit` 封顶（列表 200 / 指标点 2000）。不设流式、不设分页游标 —— v1 的查询都是"看一眼"。
- 实现顺序建议：端口（含 `.port` 文件）→ `/api/summary` → `/metrics`（Prometheus）→ 列表端点 →
      `readout/payload` 解码 → `/api/self-log` → `/` 页面。
      每一段都能独立验收，不必等全部写完。鉴权按第四节实现（**默认关**，因此不占前三段的时间）。
