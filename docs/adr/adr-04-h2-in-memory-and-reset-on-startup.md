# H2 用内存模式，存储随进程存活；因此启动时必须显式重置环形文件

表头数据的落地形态选 **H2 内存模式**（`jdbc:h2:mem:` + `DB_CLOSE_DELAY=-1`）。这与 ADR-1 的有界预算一致：表头侧靠行数水位（`rows.traces` / `rows.logs`）封顶，载荷侧靠环形文件封顶，两侧都不需要落盘即达到上限。

但这个选择有一个连带后果，不定清楚就会变成隐性行为。

`CappedFileStorage.openAndInit()` 在文件长度匹配时会**保留 `currIndex`**（16B 文件头是跨重启持久化的）。而 H2 内存模式重启即失 —— 于是重启之后：表头行全空，没有任何 `payload_id` 指向环里的块；**环里的块可读但无人引用，且它们来自上一个进程**。新写入从 `currIndex` 继续，绕满一圈后自然覆盖，所以容量不会泄漏；但"新进程能读到旧进程写的字节"这件事会**偶然发生**，因为没人声明过它。

**决策**：**存储随进程存活。重启即清空 —— 两个存储层一起清。** 启动时若检测到数据目录里已有环形文件，显式重置它（清零 `currIndex`），而不是靠 H2 空了"顺带"没人引用。

## 为什么不让表头落到磁盘

- **文件锁是硬伤。** H2 file 模式在多进程 / 多实例下会撞锁。本产品的定位是"挂在客户应用进程内"，一个应用起两个实例、或应用与运维脚本同时打开数据目录，都会撞上；这类故障极难排查。
- **落盘就把"数据出堆"变成默认。** 定位是单 JVM、随应用生死。表头落盘会引入"应用崩了但文件还在"的半存活状态，反而要额外定义一致性。
- **跨重启保留不是本产品的卖点。** 有界成本、单 JVM、不发往远端 —— 这三条已经足够差异化。为了"重启还在"引入文件锁与半存活状态，代价大于收益。

**代价**：应用重启后看不到重启前的 trace 与指标。这是**明确声明的产品性质**，不是缺陷，因此必须在 README 与读口里写清（读口显示的 uptime 从本次启动算起）。

## 为什么不是"扫环重建表头"

理论上可行：payload 里就是编码后的 OTLP bytes，trace_id / span_id 都在里面，启动时顺序扫环解码、重建表头行，就能做到跨重启保留。**明确不做**，理由：

- **启动时间与环大小成正比。** 256 MiB 的环在每次启动都要扫一遍、解一遍 proto —— 而"应用启动快"是被依赖的东西。
- **需要一个开关，一旦有人打开就会怪它。** "默认清空，但有个配置能保留"意味着两条路径都要长期测；而保留路径没有任何真实用户。
- **两层的"新鲜度"会不一致。** 表头来自上一次进程、载荷也是上一次进程，但 agent 侧的 SDK 计数、内存热层全是本次的 —— 读口会呈现一个混合体，排查时反而更难定位。

## Consideres Options（保留项）

- **H2 file 模式，表头落盘**：拒绝。见上面三条。
- **mem 模式 + 保留环形文件现状（不清零）**：拒绝。这正是本文要修的隐性行为 —— 语义上等于"半保留"，且没人声明过。
- **mem 模式 + 启动时扫环重建表头**：拒绝。启动开销与长期测试成本都高于一个未被要求的能力。
- **表头也放环形文件，不用 H2**：拒绝。查询要按 trace_id、按 scope、按时间过滤，顺序扫环做不到；H2 在这里是必需品而不是优化。

## Consequences

- **存储层需要一个显式的"重置"入口**，在数据目录初始化时被调用一次。这是本决策的直接产物，不是可选项。
- 数据目录的语义变成"**每次启动都是空的**"，因此目录里只会有当次启动写出的东西。运维排查时可以直接 `ls` 确认，不需要解析文件内容。
- 跨重启保留如果将来变成真需求，路径是**换存储形态**（表头落盘或扫环重建），而不是给这个决定加开关。
- 与 ADR-3 的关系：第 2 种形态（环形覆盖）的计数随进程归零，读口不该把它当成"累计值"展示。
