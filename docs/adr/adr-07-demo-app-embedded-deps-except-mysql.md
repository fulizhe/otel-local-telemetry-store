# demo-app 的依赖全部内嵌，唯一例外是 MySQL —— 例外必须降级而不是拖垮进程

demo-app 要造出 H2 / Redis / Kafka / gRPC / MySQL 五类外部依赖的调用样例，
用来验证「agent 自带仪表化在真实客户端库上挂得上 span」，并最终在读口的链路图上看出调用链。

## 面对什么

每个依赖都要回答一个问题：**服务端在哪？**

| 依赖 | 有没有嵌入式实现 | 结论 |
| --- | --- | --- |
| H2 | 本来就是库 | 内嵌 |
| Redis | `it.ozimov:embedded-redis`（jar 内含各平台 `redis-server`） | 内嵌 |
| Kafka | `kafka_2.13` 的 **KRaft 单节点**模式 | 内嵌 |
| gRPC | Netty server 起在真端口上 | 内嵌 |
| **MySQL** | **没有**。没有可嵌入的 MySQL 服务端实现 | **外部** |

MySQL 是唯一没有内嵌形态的。为了链路图上能认出「这次调的是哪个数据库」，
H2 与 MySQL 两跳都必须真实存在 —— 只做 H2，图上就只有一种库，验证不了这件事。

## 怎么定

**前四个内嵌，MySQL 连用户环境里已有的实例（默认 `127.0.0.1:13306`），连不上就降级。**

「降级」的具体口径必须写死，否则会变成「MySQL 没起来 → 端点 500 → 忘了它是外部依赖」：

- 启动时**探测一次**连不连得上，结果只进 `/demo/deps/status` 的 `ready` / `detail` 字段。
- **探不通不抛异常、不重试、不阻塞启动** —— demo-app 的进程照常起来。
- 调用端点在库不可用时返回**明确的降级说明**（哪一项、为什么），而不是 500 或超时。
- 链路图上**不会出现 MySQL 那一跳**，且这件事**在 `/demo/deps/status` 里能提前看到**，
  不会让人对着空图猜「是埋点没挂上还是库没起来」。

## Considered Options（保留项）

- **用 docker 起 MySQL，端口写死 13306**：这就是本决策。不写进仓库的 compose，
  因为 demo-app 的其余依赖都不需要它 —— 让 demo-app 依赖一个外部中间件已是既定取舍，
  再让它依赖一个仓库内的编排文件会把取舍扩大。
- **MySQL 也内嵌（MariaDB4j 之类）**：明确不做。这类库是把一个真实数据库的二进制塞进 jar，
  版本漂移、体积、以及「跑起来了但行为和 MySQL 不一样」的风险都高于它在这个靶子里的价值。
- **只做 H2，不做 MySQL**：拒绝。见上面「面对什么」—— 图上认不出库。
- **把 `db.system` 提成 `span` 表的一列，图上画成徽标**：**后置**。
  第一版靠 SQL 里的表名区分（`demo_h2_order` / `demo_mysql_order`），
  span name 就是 SQL，图上直接读得出来，**不用动存储层**。
  真觉得不够再加列 —— 那会碰到 ADR-2（表头行只留可查询字段），值得单独一条决策。
- **MySQL 也做成「进程内 H2 用 MySQL 兼容模式」**：这仍然是 H2，不是 MySQL。拒绝。

## Consequences

- **demo-app 从「零外部进程」变成「有一个外部依赖」**。这是本决策否掉的原口径，
  换来的东西是链路图上能区分两种数据库。
- 换机器时若没有那个 MySQL 实例，**四跳照常工作**，只是链路图少一跳 —— 这是预期行为，不是故障。
- `127.0.0.1:13306` 与库名 `demo` 是**本机约定**，需要可配置（配置名带 `otel.localstore.` 前缀不行 ——
  它不属于本扩展的配置命名空间，见 README），但**配置永不失败**：非法取值回落默认值，不抛异常。
- 依赖健康状态**不进 `self.html`**。读口不该认识 demo-app 的东西（ADR-6 的封闭清单原则）。
- demo-app 是靶子不是交付物，因此这套「起不来就降级」的口径不推广到主工程。
